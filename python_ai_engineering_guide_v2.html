🧠 Dynamic Typing — No Declarations
Variables are labels, not typed slots
Python infers types at runtime. There is no int x = 5. Variables are re-bindable to any type. This is NOT a weakness — Python 3.9+ has full type hint support for IDE checking and documentation without runtime cost.
"A variable is a sticky note, not a typed box. Stick it anywhere."
Java 
String name = "Bhanu";
int age = 35;

List<String> items;
Optional<String> val;
Python 
name = "Bhanu"   # str
age  = 35       # int
# re-bind anytime:
items: list[str] = []
val: str | None = None
Use type hints + mypy for static analysis. The runtime ignores them, but your IDE and team won't.

🦆 Duck Typing & Protocols — No Interfaces
Structural typing: if it has the method, it works
Python has no implements keyword. Objects are compatible if they have the right methods. Use Protocol (PEP 544) as a structural interface — the class never mentions the Protocol, yet type checkers validate it. Use ABC for enforced abstract base classes.
"Don't check the type. Check the behaviour. If it quacks, it's a duck."
from typing import Protocol

class LLMBackend(Protocol):          # ≈ Java interface
    def complete(self, prompt: str) -> str: ...
    def embed(self, text: str) -> list[float]: ...

class OpenAIBackend:            # no "implements"!
    def complete(self, prompt: str) -> str:
        return openai.chat(prompt)
    def embed(self, text: str) -> list[float]:
        return openai.embed(text)

def run_agent(backend: LLMBackend):   # accepts any conforming class
    return backend.complete("Hello")

🎀 Decorators — AOP Without a Framework
Wrap functions transparently — think @Cacheable, @Retry, @Logged
A decorator is a function that takes a function and returns a new function. Python applies it at import time. This is how LangChain's @tool, FastAPI's @app.route, and retry libraries all work.
"@decorator = AOP around-advice without XML or proxies."
import functools, time, logging

def retry(max_attempts=3):           # parameterised decorator
    def decorator(func):
        @functools.wraps(func)         # preserves __name__ etc.
        def wrapper(*args, **kwargs):
            for attempt in range(max_attempts):
                try: return func(*args, **kwargs)
                except Exception as e:
                    if attempt == max_attempts-1: raise
                    time.sleep(2**attempt)  # exponential backoff
        return wrapper
    return decorator

@retry(max_attempts=3)               # ≈ @Retry(maxAttempts=3)
def call_llm(prompt: str) -> str:
    return openai_client.complete(prompt)

🔄 Generators & yield — Lazy Iterators
yield pauses a function and remembers state — critical for LLM streaming
Java's Iterator requires a full class with hasNext() and next(). Python's yield turns any function into a lazy iterator. When an LLM streams tokens, Python generators are the natural fit.
"yield = pause here, hand back a value, resume when asked."
def fibonacci():                # infinite generator!
    a, b = 0, 1
    while True:
        yield a                   # pauses, returns a
        a, b = b, a + b

fib = fibonacci()
print([next(fib) for _ in range(6)])  # [0,1,1,2,3,5]

# LLM streaming — this is exactly how Anthropic SDK works:
def stream_llm(prompt: str):
    with client.messages.stream(prompt=prompt) as stream:
        for text in stream.text_stream:
            yield text            # caller gets tokens one by one

🔒 Context Managers — try-with-resources, Evolved
with = borrow, use, auto-return — even on exceptions
Python's with statement is Java's try-with-resources but more general. Any object implementing __enter__ and __exit__ works. In AI systems, use this for DB connections, file handles, API session clients, and tracing spans.
"with = borrow it, use it, auto-return it. No finally needed."
Java 
try(var r = getResource()) {
  r.doWork();
} // auto-closed
Python 
with get_resource() as r:
    r.do_work()
# auto-closed
from contextlib import contextmanager

@contextmanager
def llm_trace(name: str):
    span = tracer.start(name)       # __enter__: setup
    try:
        yield span                  # caller's body runs here
    except Exception as e:
        span.record_error(e)
        raise
    finally:
        span.finish()               # __exit__: always runs

# Multiple contexts in one line:
with open("in.txt") as src, open("out.txt", "w") as dst:
    dst.write(src.read())

🏗 Classes & Dataclasses — Java Records, Evolved
Python classes are simpler; @dataclass removes all boilerplate
Python classes don't need getters/setters, explicit constructors for simple cases, or equals() boilerplate. @dataclass auto-generates __init__, __repr__, __eq__. Pydantic (Phase 2) adds validation on top.
from dataclasses import dataclass, field

@dataclass
class ChatMessage:
    role:    str                      # required arg
    content: str                      # required arg
    tokens:  int  = 0                # optional, default 0
    meta:    dict = field(           # mutable default needs field()
        default_factory=dict)        # ← never use default={}

m = ChatMessage("user", "Hello AI")
print(m)  # ChatMessage(role='user', content='Hello AI', ...)
print(m == ChatMessage("user", "Hello AI"))  # True (auto __eq__)

# Full class with property (≈ Java getter/setter)
class Agent:
    def __init__(self, name: str):
        self._name = name           # _ = private by convention

    @property
    def name(self) -> str:
        return self._name.upper()  # ≈ getName() but as attribute
💡 Rule: Use @dataclass for plain data holders. Use Pydantic BaseModel when you need validation or JSON serialisation (LLM output parsing).
🛡 Exception Handling — Resilient Agent Calls
No checked exceptions — but structured handling is still critical
Python has no checked exceptions (no throws clause). All exceptions are unchecked. For AI agents, you need structured retry / fallback logic around LLM API calls that can fail with rate limits, timeouts, or malformed outputs.
"Catch what you can fix. Let unexpected errors crash loudly and log."
import anthropic

try:
    response = client.messages.create(...)
except anthropic.RateLimitError:
    time.sleep(60); retry()       # 429 — back off
except anthropic.APITimeoutError:
    use_fallback_model()           # timeout — switch
except (ValueError, KeyError) as e:
    log.error(f"Parse error: {e}")  # bad LLM output
else:
    process(response)             # runs ONLY if no exception
finally:
    metrics.record()              # always runs (like finally)

⚠️ The GIL — Python's Most Misunderstood Rule
Global Interpreter Lock: one thread runs Python bytecode at a time
The GIL means Python threads can't run Python code in parallel on multiple CPU cores. But for AI engineering, almost all work is I/O-bound (network calls to LLM APIs), so the GIL rarely matters. NumPy and PyTorch release the GIL during C-level computation, so they're fine too.
"GIL kills CPU parallelism. asyncio and NumPy sidestep it entirely."

🔢 NumPy — Stop Looping, Start Broadcasting
Vectorised C-speed math on typed arrays — the engine of all ML
NumPy's ndarray is a typed, fixed-shape array backed by contiguous memory — like a Java int[] but N-dimensional. Broadcasting means operations apply across entire arrays without Python loops. This is why ML code is fast despite Python being slow — the loops run in C.
"Stop writing Python loops over numbers. Let NumPy loop in C at 100× speed."
import numpy as np

# 1D array — like a typed int[] or double[]
a = np.array([1.0, 2.0, 3.0, 4.0], dtype=np.float32)
print(a * 2)           # [2. 4. 6. 8.] — no loop!
print(a.mean(), a.std()) # 2.5, 1.118
print(a[a > 2])          # [3. 4.] — boolean mask (fancy indexing)

# 2D: think ML feature matrix (rows=samples, cols=features)
m = np.array([[1,2,3],
              [4,5,6]])       # shape: (2, 3)
print(m.shape)              # (2, 3)  ← always check shape!
print(m[0, :])              # row 0:  [1, 2, 3]
print(m[:, 1])              # col 1:  [2, 5]

# Common AI shapes you'll encounter:
np.zeros((32, 512))         # batch=32, embed_dim=512
np.random.randn(4, 8, 64) # (batch, seq_len, hidden_dim)

# Broadcasting: shapes align right-to-left
vec = np.array([10, 20, 30]) # shape (3,)
print(m + vec)              # adds vec to each row of m
🧠 Key shapes in AI: (batch, seq) (batch, features) (seq, embed_dim) (n_heads, seq, seq). Always print .shape when debugging ML code.

✅ Pydantic — The Backbone of Every AI System
Typed, validated, serialisable models — used everywhere in AI pipelines
Pydantic is the single most important library for AI engineering. It does what Java's record + @Valid + Jackson combined do, but in 3 lines. Every serious AI framework (LangChain, FastAPI, the Anthropic SDK) uses Pydantic internally. Structured LLM output parsing relies on it completely.
"Pydantic = Java record + Bean Validation + Jackson. In 3 lines."
from pydantic import BaseModel, Field, model_validator
from typing import Literal

class ToolCall(BaseModel):            # ≈ Java record
    tool_name: str
    arguments: dict[str, str]
    confidence: float = Field(
        ge=0.0, le=1.0,               # ≈ @DecimalMin @DecimalMax
        description="0–1 confidence")

class AgentResponse(BaseModel):
    action:  Literal["tool_call", "answer"]  # enum-like
    tool:    ToolCall | None = None

    def check_tool(self):
        if self.action == "tool_call" and not self.tool:
            raise ValueError("tool required")
        return self

⚡ asyncio — CompletableFuture for Python
Single-threaded event loop: make 100 LLM calls with zero thread overhead
Python's async model uses a single-threaded event loop (like Node.js). async def defines a coroutine. await suspends it while waiting for I/O, letting other coroutines run. This is how you fire off 50 parallel LLM API calls without 50 threads.
"async def = coroutine (lazy promise). await = yield CPU while waiting for I/O."

      callLLM("p2")));

  .allOf(futures...).join();
Python 
import asyncio

async def main():
    results = await asyncio.gather(
        call_llm("p1"),
        call_llm("p2"),

# gather ≈ allOf()
import asyncio, httpx

async def call_llm(prompt: str) -> str:
    async with httpx.AsyncClient() as client:
        r = await client.post("https://api.anthropic.com/...",
                               json={"prompt": prompt})
        return r.json()["content"]

async def batch_evaluate(prompts: list[str]) -> list[str]:
    # Fire all calls concurrently, wait for all to finish
    return await asyncio.gather(*[call_llm(p) for p in prompts])

# Run in a script (entry point):
asyncio.run(batch_evaluate(["Q1", "Q2", "Q3"]))
⚠️ Golden rule: Once you use async def, everything calling it must also be async def. You cannot await from a regular function. Start async at the top and let it flow down.

🤖 Anthropic & OpenAI SDK — Calling LLMs from Python
LLM API = typed REST client with message-role protocol
The Anthropic and OpenAI SDKs are well-designed typed clients. Messages follow a strict role-based protocol: system sets the AI's persona/instructions, user sends the human turn, assistant holds prior AI replies. Think of it like a structured HTTP request where the body is a conversation thread.
"system = config. user = request. assistant = prior response. Chain them for memory."
import anthropic

client = anthropic.Anthropic()    # reads ANTHROPIC_API_KEY from env

# Basic call — synchronous
msg = client.messages.create(
    model    = "claude-sonnet-4-6",
    max_tokens = 1024,
    system   = "You are a senior Java engineer teaching Python.",
    messages = [
        {"role": "user", "content": "Explain generators in Python."}
    ]
)
print(msg.content[0].text)          # the response text

# Multi-turn: maintain conversation history
history = []
def chat(user_input: str) -> str:
    history.append({"role": "user", "content": user_input})
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=512,
        messages=history          # pass the whole history
    )
    reply = resp.content[0].text
    history.append({"role": "assistant", "content": reply})
    return reply

# Async version (for batch processing):
import anthropic
aclient = anthropic.AsyncAnthropic()
async def async_chat(prompt: str) -> str:
    msg = await aclient.messages.create(
        model="claude-sonnet-4-6", max_tokens=512,
        messages=[{"role": "user", "content": prompt}])
    return msg.content[0].text

🔧 Tool Calling — LLM-Driven Function Dispatch
Tool calling = the LLM decides which function to call and with what arguments
Tool calling (function calling) is the core primitive of agentic systems. You define tools as JSON schemas (like RPC IDLs), the LLM decides which to call, you execute it, and return the result. The LLM orchestrates; your code executes. This is the fundamental agent loop.
"Define the tools. Let the LLM dispatch. You just execute. That's the agent loop."
# Step 1: Define tools as JSON schema (≈ RPC method specs)
tools = [{
    "name": "search_codebase",
    "description": "Search the codebase for a pattern",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "regex pattern"},
            "path":  {"type": "string", "description": "directory to search"}
        },
        "required": ["query"]
    }
}]

# Step 2: LLM decides whether/which tool to call
response = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=512,
    tools=tools,
    messages=[{"role": "user",
               "content": "Find all usages of sys_attachment in glide/"}]
)

# Step 3: Check if LLM wants to call a tool
if response.stop_reason == "tool_use":
    tool_block = next(
        b for b in response.content
        if b.type == "tool_use")
    tool_name = tool_block.name      # "search_codebase"
    tool_args = tool_block.input      # {"query": "sys_attachment"}

# Step 4: Execute and return result to LLM
result = tool_registry[tool_name](**tool_args)
messages.append({"role": "user", "content": [{
    "type": "tool_result",
    "tool_use_id": tool_block.id, "content": str(result)
}]})

Force LLMs to return validated, typed data — never parse free-text in production

🔍 Embeddings — Meaning as Numbers
Convert text to dense vectors that encode semantic meaning
An embedding is a fixed-length list of floats (e.g. 1536 dimensions) that represents the meaning of a piece of text. Similar meanings produce similar vectors. This is how semantic search works: find vectors close to the query vector rather than matching keywords. Think of it as "is-near-in-concept" instead of LIKE '%keyword%'.
"Embeddings = GPS coordinates for meaning. Nearby coords = nearby concepts."
import anthropic
import numpy as np

client = anthropic.Anthropic()

# Generate embeddings (Voyage AI via Anthropic)
from voyageai import Client
vo = Client()
docs = ["Python generators pause execution",
        "Java iterators use hasNext/next",
        "async/await yields control"]

result  = vo.embed(docs, model="voyage-3")
vectors = np.array(result.embeddings)  # shape: (3, 1024)

# Cosine similarity: how similar are two meanings?
def cosine_sim(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# Generators vs iterators: very similar (≈ 0.92)
print(cosine_sim(vectors[0], vectors[1]))

# Practical: find most relevant doc for a query
query_vec = np.array(vo.embed(
    ["how to lazily generate values"],
    model="voyage-3").embeddings[0])
sims    = vectors @ query_vec    # dot product with all docs
best    = np.argmax(sims)        # index of most similar doc
print(docs[best])                # "Python generators pause execution"

🗄 Vector Databases — Semantic Search at Scale
Store millions of embeddings; query by semantic similarity in milliseconds
A vector database is like a distributed index over embedding space. Instead of B-tree index on a key, it uses approximate nearest-neighbour (ANN) algorithms (HNSW, IVF) over float arrays. For AI agents, the vector DB is the long-term memory — it stores chunked documents that the agent retrieves at query time.
"Vector DB = semantic search index. Nearest neighbour, not keyword match."
# ChromaDB: local, dev-friendly vector store
import chromadb

db   = chromadb.Client()
coll = db.create_collection("glide_docs")

# Index your docs (add embeddings + metadata + source text)

    ids        = ["doc1", "doc2"],
    documents  = ["GlideRecord queries the DB table",
                  "sys_attachment stores file blobs"],
    metadatas  = [{"source": "wiki", "page": 42},
                  {"source": "wiki", "page": 88}]
)

# Semantic search: find top-3 most relevant docs
results = coll.query(
    query_texts = ["how do I query a ServiceNow table"],
    n_results   = 3
)
print(results["documents"])  # ranked by similarity

📚 RAG — Retrieval-Augmented Generation
Give the LLM your private data at query time — no fine-tuning required
RAG (Retrieval Augmented Generation) is the dominant pattern for grounding LLMs in private or up-to-date data. The flow: chunk your docs → embed each chunk → store in vector DB → at query time, retrieve top-K similar chunks → inject into prompt → LLM answers with context. Think of it as just-in-time loading of relevant memory into the model's context window.
"RAG = give the LLM just-in-time notes from your private library."
# Full RAG pipeline in Python
def chunk_text(text: str, size=500) -> list[str]:
    # Split into overlapping chunks of ~500 chars
    words = text.split()
    return [" ".join(words[i:i+size]) for i in range(0, len(words), size-50)]

def build_index(documents: list[str]):
    collection = chroma_db.create_collection("kb")
    all_chunks  = [c for doc in documents for c in chunk_text(doc)]
    collection.add(documents=all_chunks,
                   ids=[str(i) for i in range(len(all_chunks))])
    return collection

def rag_answer(question: str, collection) -> str:
    # 1. Retrieve top-3 relevant chunks
    hits    = collection.query(query_texts=[question], n_results=3)
    context = "\n\n".join(hits["documents"][0])
    # 2. Inject context into prompt
    prompt  = f"""Use the context below to answer the question.
If unsure, say "I don't know".
Context: {context}
Question: {question}"""
    # 3. LLM answers with grounded context
    return call_llm(prompt)

🌊 Streaming — Real-time Token Output
Stream tokens as they're generated — better UX and lower time-to-first-token
LLMs generate one token at a time. Streaming delivers each token as it's produced rather than waiting for the full response. This is critical for interactive UIs and agentic thought visibility. Both the Anthropic SDK and OpenAI SDK support streaming via context managers and generators.
"Don't wait for the full response. Stream tokens like a log tail."
# Sync streaming with Anthropic SDK
with client.messages.stream(
    model      = "claude-sonnet-4-6",
    max_tokens = 1024,
    messages   = [{"role": "user", "content": prompt}]
) as stream:
    for text in stream.text_stream:  # generator of tokens
        print(text, end="", flush=True)

Phase 4 — Agentic Systems
🤖 The Agent Loop — Distributed Systems You Already Know
Agent = LLM + Tools + Memory + Loop. It's a microservice with a reasoning engine.
An AI agent is just a loop: observe → reason → act → observe again. The LLM is the reasoning engine; tools are external services it can call; memory is state management. As a distributed systems engineer, you already know the hard problems — consistency, fault tolerance, observability — they apply here exactly the same way.
"Agent loop = event-driven microservice where the event handler is an LLM."
from anthropic import Anthropic

def run_agent(user_goal: str, tools: dict) -> str:
    client   = Anthropic()
    messages = [{"role": "user", "content": user_goal}]
    tool_specs = [get_spec(t) for t in tools.values()]

    while True:                           # the agent loop
        resp = client.messages.create(
            model="claude-sonnet-4-6", max_tokens=4096,
            tools=tool_specs, messages=messages)

        if resp.stop_reason == "end_turn":   # done — return answer
            return resp.content[0].text

        # LLM wants to call tools — execute them
        tool_results = []
        for block in resp.content:
            if block.type == "tool_use":
                fn     = tools[block.name]    # dispatch by name
                result = fn(**block.input)    # execute
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": str(result)
                })
        # Append LLM turn + tool results, loop again
        messages += [
            {"role": "assistant", "content": resp.content},
            {"role": "user",      "content": tool_results}
        ]
🔁 Loop guard: Always add a max_iterations safeguard. Agents can loop forever on ambiguous goals — treat it like a circuit breaker for infinite retries.
🧠 Memory Patterns — State Management for Agents
Short-term = context window. Long-term = vector DB or KV store.
Agents have two memory tiers. Short-term: the conversation history (messages list) — fast, expensive per-token, lost when context fills. Long-term: external storage queried at runtime — unlimited, but retrieval adds latency. This maps exactly to L1/L2 cache vs heap in distributed systems thinking.
"Context window = L1 cache (fast, tiny). Vector DB = disk (slow, unlimited)."
class AgentMemory:
    def __init__(self, max_turns=20):
        self.short_term  = []           # sliding window of messages
        self.long_term   = ChromaDB()  # vector store for summaries
        self.max_turns   = max_turns

    def add(self, message):
        self.short_term.append(message)
        if len(self.short_term) > self.max_turns:
            old = self.short_term.pop(0)  # evict oldest
            self.long_term.add(old)       # archive to vector store

    def recall(self, query: str) -> list:
        # Retrieve relevant past context at query time
        return self.long_term.query(query, n=3)
🔬 LangChain & LangGraph — When to Use a Framework
Use frameworks for complex multi-agent graphs. Use raw SDK for simple agents.
LangChain provides abstractions for chains, retrievers, and tool-calling. LangGraph models agents as directed graphs with cycles — useful for multi-agent systems where agents hand off to other agents. Rule of thumb: if your agent logic fits in 100 lines, use the raw SDK. Add LangChain when you need a retriever pipeline, multi-agent routing, or built-in retry/fallback logic.
# LangChain: simple RAG chain
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate

    ("user",   "{input}"),
])
chain  = prompt | llm   # pipe operator = chain composition
result = chain.invoke({"input": "Explain RAG in 2 sentences"})

📡 Observability — Your p99 Latency for Agent Systems
Trace every LLM call, tool call, and agent decision — or debugging is impossible
Agent systems are non-deterministic. Without tracing, debugging why an agent made a wrong decision is like debugging a distributed system with no logs. LangSmith and Langfuse give you traces showing each LLM call's inputs, outputs, token usage, latency, and tool call chain. This is non-negotiable in production. Think of it like your Jaeger/Zipkin for agents.
"If you can't trace it, you can't debug it. Instrument first, optimise second."
# Langfuse: open-source LLM observability
from langfuse import Langfuse
from langfuse.decorators import observe, langfuse_context

lf = Langfuse()           # reads LANGFUSE_* env vars

@observe()                 # auto-traces this function
def agent_step(prompt: str) -> str:
    response = call_llm(prompt)
    # Log custom metadata to the trace:
    langfuse_context.update_current_observation(
        metadata={"step": "planning", "tools_available": 4})
    return response
